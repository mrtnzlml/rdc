# Native macOS app — Phase 2: SwiftUI app (`macos/`)

**Date:** 2026-06-30
**Status:** Designed — pending implementation
**Area:** new `macos/` SwiftUI app consuming the `rdc-ffi` UniFFI bridge
**Parent spec:** `docs/superpowers/specs/2026-06-29-native-macos-app-design.md`
**Builds on:** Phase 1 (`docs/superpowers/plans/2026-06-29-native-macos-app-phase1-rdc-ffi.md`) — merged

## Problem

Phase 1 removed the old Tauri/React desktop app and built `rdc-ffi`, an in-process
UniFFI bridge exposing the rdc core to Swift, plus `build-xcframework.sh` (validated:
it produces `rdc_ffi.xcframework` + `generated/rdc_ffi.swift`). There is **no runnable
GUI yet** — Phase 2 is the actual native macOS app.

The generated Swift surface this app consumes (verified from the built bindings):

```swift
func listConnections(parent: String) -> [ConnectionSummary]                       // no throw
func addConnection(parent: String, input: AddConnectionInput) throws -> ConnectionSummary
func editCredentials(folder: String, input: EditCredentialsInput) throws
func validateExistingProject(path: String) throws -> ConnectionSummary
func syncConnection(folder: String, apiBase: String, orgId: UInt64, progress: SyncProgress) throws -> SyncResult
func ffiVersion() -> String?

struct ConnectionSummary { id, name, apiBase: String; orgId: UInt64; folder: String; authKind: AuthKind; lastSyncUnix: Int64?; fileCount: UInt64 }
struct AddConnectionInput { name, apiBase: String; orgId: UInt64; authKind: AuthKind; token, username, password: String? }
struct EditCredentialsInput { authKind: AuthKind; token, username, password: String? }
struct SyncResult { fileCount: UInt64 }
enum AuthKind { case token, password }
enum FfiError: Error { case Operation(message: String) }   // thrown by add/edit/validate/sync
enum SyncPhase { case started, done(fileCount: UInt64), error(message: String) }
protocol SyncProgress: AnyObject { func onPhase(phase: SyncPhase) }
```

`ConnectionSummary.id` is the folder slug (good for SwiftUI `Identifiable`). Sync takes
a `SyncProgress` callback and **blocks**, so it must run off the main thread.

## Goal

A launchable, sandbox-first SwiftUI app ("Rossum Local") with **full parity** to the old
seven operations, generated by **XcodeGen** from a committed `project.yml`, targeting
**macOS 15**, linking the `rdc_ffi.xcframework`. The on-disk contract stays identical so the
CLI and app interoperate on the same folders.

## Non-goals (deferred)

- No new features beyond the seven operations (no push/bidirectional sync, no multi-env).
- No Keychain migration — secrets stay in the on-disk format (via the FFI).
- No App Store submission / Developer ID / notarization in this phase — build & run locally
  with free Personal Team signing; the sandboxed app is MAS-ready when a membership is added.
- No reimplementation of any rdc logic in Swift — all sync/credential/scaffold work goes
  through the FFI.

## Decisions

1. **Project tooling:** XcodeGen. `macos/project.yml` (committed) → `RossumLocal.xcodeproj`
   (generated, gitignored). `brew install xcodegen`.
2. **UI scope:** full parity (all seven ops + add/edit sheets + context menu + remove-confirm
   + empty state + native menu bar / Dock badge / completion notifications / sidebar vibrancy).
3. **Minimum macOS:** 15 (Sequoia) — newest SwiftUI APIs, simplest code.
4. **Identity preserved:** bundle id `ai.rossum.local`, product name "Rossum Local", app icon
   from `assets/icons/icon.png`.
5. **Sandbox-first**, free local signing now; MAS later with no architectural change.
6. **Build prerequisite:** `rdc-ffi/build-xcframework.sh` must run before generating/building
   the Xcode project (produces the linked artifact + bindings).

## Architecture

```
┌──────────────────────────────────────────────────────────┐
│  SwiftUI app  (macos/RossumLocal)                          │
│                                                            │
│  RossumLocalApp ── .commands (menu bar)                    │
│       │                                                    │
│  ContentView (NavigationSplitView)                         │
│   ├─ SidebarView (List + .contextMenu)                     │
│   └─ DetailView (fields + actions) ── sheets               │
│       │ binds to                                           │
│  @Observable ConnectionStore  ◄── single UI source of truth│
│       │ calls                                              │
│  RdcBridge / SyncCoordinator   (security-scope wrapping,   │
│       │                          threading, SyncProgress)  │
│  BookmarkStore (UserDefaults)  ── security-scoped bookmarks │
└───────┼────────────────────────────────────────────────────┘
        │ generated Swift bindings + linked
┌───────▼────────────────┐
│  rdc_ffi.xcframework    │  (Phase 1; wraps the rdc core)
└────────────────────────┘
   on disk: rdc.toml · secrets/main.secrets.json · envs/main · .rdc/state  (shared with CLI)
```

### Units (one responsibility each)
- **`ConnectionStore`** (`@Observable`): `connections: [ConnectionSummary]`, `parentFolder: URL?`,
  per-connection sync phase, surfaced error. The only state the views read. Knows nothing about
  bookmarks or threads — it asks `RdcBridge`/`SyncCoordinator` and stores results.
- **`RdcBridge`**: wraps the synchronous FFI calls (`list/add/edit/validate`). Activates the
  correct security scope around each call; runs on a background `Task`; returns to `@MainActor`.
  Maps `FfiError` → a displayable message.
- **`SyncCoordinator`** + **`SyncProgressBridge: SyncProgress`**: runs the blocking
  `syncConnection` on `Task.detached`, holding the security scope for the whole call; `onPhase`
  hops to `@MainActor` to update the store, Dock badge, and post the completion notification.
- **`BookmarkStore`**: persists/resolves security-scoped bookmark data (the parent folder + each
  external project) in `UserDefaults`, with `bookmarkDataIsStale` handling.
- **Views**: pure presentation bound to `ConnectionStore`.

### Threading & security scope
`syncConnection` blocks and invokes `onPhase` on the calling thread, so the app calls it from
`Task.detached`; `SyncProgressBridge.onPhase` dispatches to `@MainActor`. All FFI file access is
bracketed by `startAccessingSecurityScopedResource()` / `stopAccessingSecurityScopedResource()`
on the relevant folder URL — for sync, the bracket spans the entire (long-running) call.

## Discovery model

The displayed connection list is the union of two sources:
1. **Managed connections:** `listConnections(parentURL)` — folders the user created via *Add*,
   living under the granted parent folder.
2. **Externally-attached projects:** for each external bookmark, resolve its URL and run
   `validateExistingProject(path)`; include the returned summary.

Operation semantics:
- **Add** → `addConnection(parentURL, input)` (lands under the parent).
- **Open Existing** → `NSOpenPanel` picks a folder → `validateExistingProject(path)` validates it
  → store a security-scoped bookmark → it appears in the list. No symlink, no copy.
- **Edit credentials / Sync / Reveal** → operate on the connection's own `folder` under the
  appropriate active scope.
- **Remove** → if the connection is under the parent: `FileManager.trashItem` (recoverable). If
  it is an externally-attached project: drop its bookmark only — **never** trash the user's folder.

## Sandbox & entitlements

`RossumLocal.entitlements`:
- `com.apple.security.app-sandbox` = true
- `com.apple.security.network.client` = true (the rdc core makes HTTPS calls to the Rossum API
  in-process)
- `com.apple.security.files.user-selected.read-write` = true (NSOpenPanel + security-scoped
  bookmarks to user-chosen folders)

The parent folder is granted once via `NSOpenPanel` (defaulting to `~/Documents/Rossum` so CLI
interop is seamless). `BookmarkStore` is the only app-private state; it holds **access grants
only**, never connection metadata (which is always derived from disk by the FFI).

## Native touches

- **Sidebar vibrancy:** automatic with `NavigationSplitView`'s sidebar material on macOS.
- **Dock badge:** `NSApp.dockTile.badgeLabel` set to the active-sync count (cleared at zero).
- **Completion notifications:** `UNUserNotificationCenter` (request authorization on first sync;
  post "Sync complete · N files" / "Sync failed · message").
- **Menu bar:** `.commands` — `New Connection ⌘N`, `Open Existing rdc Project… ⌘O`, plus the
  standard Edit/View/Window groups.
- **Single instance:** macOS reactivates the existing instance on relaunch by default — no extra
  code.

## Build & run

```sh
rdc-ffi/build-xcframework.sh         # once, and after any rdc/rdc-ffi change
cd macos && xcodegen generate        # produces RossumLocal.xcodeproj
open RossumLocal.xcodeproj           # ⌘R — free Personal Team signing, no Developer ID needed
```

`RossumLocal.xcodeproj`, `rdc-ffi/rdc_ffi.xcframework`, and `rdc-ffi/generated/*.swift` are all
gitignored (regenerated from source). `macos/.gitignore` covers the generated project.

## Testing

- **CLI / subagent-verifiable (Xcode 26.6 `xcodebuild` is installed):**
  - `xcodebuild build` of the app target with `CODE_SIGNING_ALLOWED=NO` — compile-checks all Swift.
  - `xcodebuild test` of `RossumLocalTests` (XCTest): `BookmarkStore` store/resolve/stale; the
    parent-scan + external-bookmark list merge; `FfiError` → message mapping; relative-date
    formatting; sync-phase state transitions. Plus one FFI-against-temp-dir test that links the
    xcframework and exercises `addConnection` + `listConnections` on a temp folder (no network).
- **You-verify (manual, signed run in Xcode):** granting the parent folder; Add / Edit / Remove /
  Open-Existing / Reveal; a real `Sync` against a live env (progress → Dock badge → notification);
  and CLI↔app interop on the same folder.

## Backward-compatibility

On-disk format untouched (all I/O routes through the FFI → rdc functions; nothing reimplemented in
Swift). The CLI and app interoperate on the same folders. Bundle id `ai.rossum.local` and product
name "Rossum Local" preserved. The `BookmarkStore` (sandbox-mandated access grants) is the only new
app-private state.

## Risks / open questions

- `SyncProgress.onPhase` fires on the FFI/background thread → must hop to `@MainActor` (owned by
  `SyncCoordinator`). A missed hop would be a runtime UI-threading violation, not a compile error —
  covered by isolating the hop in one place + the manual run.
- Holding the security scope across a long sync → bracket the entire `syncConnection` call.
- Full sandbox runtime (bookmark persistence, `NSOpenPanel`) only truly validates in the signed run
  the maintainer performs; the design keeps that surface small and isolated (`BookmarkStore` +
  the open-panel call sites) so the compile + XCTest gate catches the rest.

## Out of scope / future

Push / bidirectional sync; multi-env projects; Keychain-backed secrets; Developer ID notarization;
Mac App Store submission; sync cancellation; finer per-file sync progress.
